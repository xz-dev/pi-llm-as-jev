## Why

`pi-continue-watchdog` and `pi-jev-todo-audit` duplicate TypeSafe System One transport, thresholds, caching, recovery and ledger plumbing, and degrade when no Jev key is available. One Pi extension should own that pipeline, support an independently selected compatible native classifier (Jev by default), and fall back to a configured tool-calling chat model, so consumers only compose business questions and act on answers.

## What Changes

- **BREAKING**: Rename the prototype native-path labels from `jev` to `classifier`: `mode` becomes `auto | classifier | llm`, `JudgeResult.backend` becomes `classifier | llm`, and `availability().jev` becomes `availability().classifier`. Update prototype configuration, clients and examples during apply; old `jev`-tagged cache/ledger entries are stale under the new backend identity and are not silently relabeled. Jev remains the default native candidate; the discrete LLM behavior is unchanged.

- New Pi extension `pi-llm-as-jev` exposing an in-process **judgment service** to other extensions: `judge(request, options)` takes Pi-shaped `state` + `choice` / `bool` / `score` questions and returns accepted answers. The service chooses a compatible native classifier or the discrete LLM backend, applies numeric policy only to the native adapter's defined confidence/probability fields, and never throws. Model type alone is not evidence of calibrated confidence.
- The service owns **exact-match raw-judgment caching, per-question native-classifier threshold policy, question AND ordered-evidence splitting, overflow recovery, and a session-branch ledger** (custom entries replayed from the active branch). Consumers supply fixed state, evidence, and questions but implement no transport or recovery loops. The selected backend/model remains part of cache, capacity and ledger identity; changing selection must not reuse another model's judgment.
- **Ordinary LLMs choose discrete business answers only**, not numeric probability or confidence estimates. Bool and probability-gated business predicates are satisfied/not-satisfied choices; existing multi-label and score questions keep their legal labels/levels. Required Pi classifier numbers are deterministic compatibility encodings, never inputs to the service's numerical gates.
- New **native classifier selection**: an optional `classifierModel` in `provider/modelid` form and a searchable picker allow selecting available Pi classifier models that support the existing question/answer contract and defined numeric-field semantics, rather than only models named Jev. Exclude this plugin's LLM-emulation provider from that native picker. Without an explicit selection, retain the existing Jev discovery preference; do not automatically replace it with an arbitrary classifier. A configured candidate unavailable in auto mode permits the existing LLM fallback; forced native mode and provider-call failures do not silently select another backend.
- New **LLM classifier backend**: a configured Pi chat model (`provider/modelid`) answers the same `choice` / `bool` / `score` questions through a discrete tool call, returned in `ClassifierResult` shape. Register the same implementation with the verified native `pi.registerProvider(provider)` overload so codemode scripts, virtual-model routers, and other extensions see it via `modelRegistry.getAvailableOfType("classifier")`. Its registered model is still LLM emulation, not a native numerical-confidence source.
- New **judge-model settings**: configure the native classifier independently of the existing LLM `model` and `thinkingLevel` settings. Both selection lists are searchable, alphabetically sorted by `provider/modelid`, and preselect the configured model in place. The chat-model picker is followed by Pi-supported thinking-level selection, including off; classifier selection does not change chat thinking settings or the main session model. Canceling changes nothing.
- Native classification calls go through `ctx.modelRegistry.classify()` instead of hand-rolled System One fetch; credentials, transport and compatible provider adapters remain Pi-owned. Capacity uses the actual selected model's context limit and verified adapter-specific constraints, without introducing a separate endpoint, calibration framework or recovery architecture.
- Consumers `pi-continue-watchdog` and `pi-jev-todo-audit` are the first adopters: they drop their transport/cache/capacity/ledger code and call the service. Their migration lands as separate changes in their own repositories; this change defines the contract they target.

## Capabilities

### New Capabilities
- `judgment-service`: In-process API other extensions call to get policy-filtered answers to Pi-shaped questions; native classifier vs LLM selection, numeric-field policy, cache, capacity splitting, overflow handling, session ledger, fail-safe result contract.
- `llm-classifier-backend`: Emulating a classifier with a tool-calling chat model; discrete output and fidelity rules; registration as a Pi classifier provider without treating compatibility numbers as native confidence.
- `judge-model-settings`: Independent native classifier and LLM model selection, chat thinking-level configuration, picker ordering/preselection/cancel safety, and persistence format.

## Impact

- **Code scope**: this repository's extension gains native-classifier selection alongside its service registry, classifier adapter, discrete LLM backend, ledger, capacity/cache, settings command and pickers. Existing pipeline architecture is retained rather than rebuilt for model selection.
- **Pi APIs used**: the verified native `pi.registerProvider(provider)` overload; `ctx.modelRegistry.classify / findOfType / getAvailableOfType / find / streamSimple`; Pi supported-thinking helpers; `pi.appendEntry` custom entries and branch replay; `ctx.ui.custom` with `SelectList` / `Input` / `fuzzyFilter`; and `Symbol.for` service discovery.
- **Consumers (separate repos, follow-up changes)**: `pi-continue-watchdog` removes `askJevChoice` / `resolveJevEndpoint` / System One constants from `src/jev-wait-gate.ts`; `pi-jev-todo-audit` removes transport, `EvaluationCache`, `envelopeKey`, `isContextOverflow` from `typesafe.ts`, all of `capacity.ts`, and the `eval` / `rejected` / `diag` ledger kinds from `ledger.ts` (keeps `receipt`). Both keep their question text and decision logic.
- **Behavioral**: Jev remains the default native candidate, while an explicitly selected compatible classifier uses its documented native confidence/named-choice-probability fields for per-caller policy, including cache hits. These values are not claimed to be uniformly calibrated across models. Ordinary LLMs choose business outcomes directly and ignore numeric thresholds; compatibility fields never claim measured certainty.
- **Dependencies**: `@earendil-works/pi-coding-agent`, `@earendil-works/pi-ai`, `@earendil-works/pi-tui` as peer/dev types only; no runtime npm dependencies.
